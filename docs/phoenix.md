# Use the tooling with Phoenix / LiveView

For a new web application, generate a normal Phoenix project in a separate
folder using the Phoenix generator you have selected. Keep its generated
application, endpoint, assets, and database setup. Transfer this template's
quality tooling into it; do not overwrite a Phoenix `mix.exs` with the OTP one.

1. Merge the nine quality dependencies and the `quality`, `quality.check`, and
   `verify` aliases from this template. Preserve Phoenix's existing `setup`,
   asset, test/database, compiler, and listener configuration.
2. Copy `.credo.exs` and the empty `.dialyzer_ignore.exs`. Merge the Dialyzer
   settings and preferred CLI environments into the generated Mix project.
3. Add `Styler` to the generated formatter's plugins; retain its HEEx plugin,
   Phoenix imports, and `*.heex` input patterns.
4. Add Tidewave as a dev dependency and insert `plug Tidewave` in a development
   conditional in the Phoenix endpoint, before the code-reloading block. Use
   the Phoenix server's `/tidewave/mcp` endpoint instead of the standalone script.
   Keep the HTTP adapter generated by Phoenix; Bandit is not needed solely for
   the standalone script once that script is removed.
5. Transfer `.github` workflows, adapting CI services and environment variables
   for your actual database. Retain the generated database setup/test aliases.
6. Adapt AGENTS.md and RULES.md to the real context names, web directory, and
   persistence contracts. Keep the full `mix verify` gate.

If using LiveView, retain its development debug annotations to help runtime tools
inspect rendered components. See the [Tidewave installation guide](https://github.com/tidewave-ai/tidewave_phoenix#installation)
for integration details for your installed version.

## Fittr conventions worth retaining

- Keep business logic in contexts and interaction state in LiveViews.
- Use `start_async/3` for expensive recomputations. Cancel superseded work before
  replacing it, set loading state, and clear it on success and exit/error paths.
- Test behavior with `Phoenix.LiveViewTest`, including errors and changing inputs.
- Label filter controls; give buttons an explicit type around forms.
- Emit operation timing telemetry with native-time `duration` and stable metadata
  keys `liveview`, `operation`, and `source`. Choose your own application prefix.
- Ensure Tailwind scans modules that return class names, including presenters
  outside the web directory when appropriate for the installed Tailwind version.
- Isolate test data per run and clean up records owned by the test. Do not copy
  Fittr's storage implementation or assume this template has a database.

## Assets and releases

Retain Phoenix's `assets.setup`, `assets.build`, and `assets.deploy` aliases. Make
`release.build` run `assets.deploy` before `release`, and invoke it with
`MIX_ENV=prod`. The Docker build must copy `assets` and any required `priv` files,
install the configured asset tools, and build assets before assembling the release.
Do not assume a developer's prebuilt static assets will exist in a clean CI clone.

Add the generated release server launcher or appropriate `PHX_SERVER` setting,
HTTP port, health checks, runtime secrets, and database migration process for your
host. The plain OTP container in this template intentionally has no web server.
